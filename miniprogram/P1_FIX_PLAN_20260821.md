## 第一批：数据完整性（本次执行）

### P1-1 sync-queue.js 三处并发缺陷

**现状**（utils/sync-queue.js:135-214）：
- flush 全程持有入口快照 `queue`；`markAsFailed()`(:105-112) 只修改存储，不动快照；
- 末尾 :211 仅当 `succeededSeqs.length > 0 || changedItems.length > 0` 才执行 `saveQueue(remaining)`，remaining 基于旧快照。

**三个缺陷**：
- a) 混合成败批次：失败项已达上限被 markAsFailed 移出存储，又被 `saveQueue(remaining)` 写回 → 复活，failed 列表每轮重复追加；
- b) 全部失败批次：不落盘 → 内存 retries 自增丢失，永达不到 MAX_RETRIES → 无限重试风暴；
- c) 长时间 await 期间其他代码 enqueue/dequeue/updateData 的写入被旧快照覆盖 → 丢任务。

**修复方案**：重构 flush 尾部为「以最新存储为骨架的统一重建」：
1. 循环内 catch：retries++；达 MAX_RETRIES 时不再调用 markAsFailed，改为收集到 `failedThisRound` 数组（seq + item）；
2. 循环后统一处理：
   - failed 存储：一次读-改-写追加 `failedThisRound` 各项；
   - `var latest = getQueue()` 取最新队列（吸收执行期间的 enqueue/dequeue/updateData）；
   - `remaining = latest.filter(q => succeededSeqs.indexOf(q.seq) < 0 && failedSeqs.indexOf(q.seq) < 0)`；
   - 对 remaining 中 seq 命中本轮快照的项：用内存项的最新 `retries` 覆盖（解决 b）；用 changedItems 的新 data 覆盖（保留图片 fileID 回写）；
   - 无条件 `saveQueue(remaining)`（解决 b 的"全失败不落盘"）。
3. `markAsFailed` 重命名为 `appendToFailed`（只写 failed 列表）；`retryFailed/clearFailed/dequeue/updateData` 不动。
**影响面排查**：markAsFailed 仅 sync-queue 内部一处调用（已 grep 确认）；对外导出签名不变。
**验证**：① node --check；② 编写 mock 冒烟脚本模拟四种场景：全成功 / 全失败连续 5 轮（第 5 轮后应进入 failed 且队列清空）/ 混合成败（失败项不得复活、failed 不得重复追加）/ flush 期间 enqueue 新项（新项必须在下一轮存活）；③ 断言 retried 计数跨轮持久。

### P1-2 mergeAndHeal「云端缺失即删」前提被打破

**现状**（utils/cloud.js:1269-1295 mergeAndHeal）：云端列表中缺失的本地已同步记录一律视为他端已删除而从本地清除。
两个被打破的场景：
- a) `fetchBrushingRecords(today)` 带日期过滤拉取 → 其余日期的已同步记录被误删；
- b) `fetchNotes` 分页中途失败仅 break（:2162-2165），用不完整的 cloudList 继续合并 → 未出现在部分结果里的笔记被误删。

**修复方案**：
1. mergeAndHeal 增加第 4 参 `{ keepLocalOnly }`：为 true 时跳过「云端缺失即本地删除」分支，仅做合并去重与墓碑过滤；
2. 所有**带过滤条件的 fetch**（先 grep 全部调用点横向排查：fetchBrushingRecords(date)、fetchNotes 分页、以及其他传参查询）改传 `keepLocalOnly: true`；
3. fetchNotes 分页失败：中止本次合并、直接返回 localNotes（下次完整拉取再合并），并 console.warn。
**影响面排查**（动手前执行）：grep `mergeAndHeal(` 全部调用点逐一分类：全量无过滤 → 维持现状；带过滤/分页 → keepLocalOnly。
**验证**：mock 场景——本地 3 条（昨天/今天各若干），云端仅返回今天的：修复前昨天记录被删，修复后保留；fetchNotes 模拟第二页抛错：本地笔记数量不变。

> **⚠️ 复核修正（外部评审 I-2）**：初版给 `fetchHabitRecords` 也传了 keepLocalOnly（理由是单页 500 截断风险），但该函数是习惯记录唯一拉取路径——keepLocalOnly 会让「云端缺失即删」对习惯记录永久失效，A 设备的删除在 B 设备永久残留。已改为照 fetchNotes 模式分页循环拉全量 + 默认合并（任何一页失败中止返回本地）。同时把 `fetchBrushingRecords` 拆分为两种策略：无 date 全量查询走分页循环+默认合并；带 date 过滤查询缺失≠删除，保留 keepLocalOnly。

### P1-3 图片上传回写下标错位（4 处同型）

**现状**（utils/cloud.js:727/733 与 2409/2414）：`uploadImages` 是过滤掉 cloud:// 后的压缩数组（原始下标存于 `img.field` 如 `images[2]`），回写却用压缩循环下标 `fullRecord.images[k]` → 混合已传/未传图时 fileID 覆盖错位、原图丢失。
**修复方案**：从 field 解析原始下标：
```js
var idxMatch = img2.field.match(/\[(\d+)\]/)
var j = idxMatch ? Number(idxMatch[1]) : k
fullRecord.images[j] = uploadRes.fileID
if (j === 0) fullRecord.imagePath = uploadRes.fileID   // 封面=images[0]，语义修正
```
tmpRecs 回写同改。两组同型位置（刷牙 :720-738、另一模块 :2400-2414）一并修改。
**验证**：mock——images 混合 [cloud://xxx, 本地路径A, 本地路径B]：断言上传后 images[1]/images[2] 分别指向对应 fileID、images[0] 保持 cloud:// 不被覆盖。

### P1-4 单例入队项成功后从不 dequeue

**现状**（utils/cloud.js:198-206）：单例乐观入队 id 形如 `singleton_<collection>_<key>`；dequeue 全项目仅 notes/drawing/habitRecord 三处调用。离线入队的旧快照在恢复联网后仍会被 flush 重传，用旧数据覆盖云端较新单例。
**修复方案**：`createSingletonSync.upload` 成功路径（callUpsertSingleton resolve 后）调用 `syncQueue.dequeue(singletonId)`，singletonId 与 enqueue 时的 id 拼接逻辑复用同一常量/函数（动手前核对 :198-206 实际拼接格式，避免拼错导致 dequeue 无效）。
**影响面**：dequeue(id) 不带 action 参数会移除该 id 全部队列项——单例 id 天然唯一，安全。
**验证**：mock——离线 enqueue 单例 → 恢复联网直传成功 → 断言队列中该项已消失。

### P1-5 stallChallenges 键名错位 + 进度永不上云

**现状**（utils/cloud.js:2066-2067）：单例配置 `storageKey: 'stallChallenges'`，而实际读写键是 `'stallDailyChallenges'`（child-storage CHILD_KEYS 内，按孩子隔离）；stall-manager.js 进度更新只写本地、启动时 fetch 结果（常为 `{}`）反向覆盖本地进度。
**修复方案**（两步配套，缺一不可）：
1. 配置 storageKey 改为 `'stallDailyChallenges'`；
2. stall-manager.js 挑战进度变更处（:337-363 更新函数尾部）调用 `uploadStallChallenges(当前进度)`——否则键名修对了云端仍无数据，fetch 依旧拿空对象覆盖本地。
**数据兼容**：云端可能残留旧键 'stallChallenges' 的孤儿单例文档——不影响运行（无人再读它），在交付说明中记录可忽略；本地旧键 'stallChallenges' 数据为空占位，无需迁移。
**验证**：mock——更新今日挑战进度 → 断言 uploadStallChallenges 被调用且读取键为 `stallDailyChallenges_<childId>`；重启流程 fetch 返回云端数据不再覆盖丢失。
